Respaldos y Recuperación ante Ataques

Guía visual de uso de los scripts — auditoría, respaldo total, PITR con binlog y el simulacro final de desastre

💼 Estos conceptos, fuera del aula

Ninguna plataforma real está exenta de un incidente grave. Lo que separa a las empresas que sobreviven de las que cierran no es evitar el desastre para siempre, sino haber practicado la recuperación ANTES de que ocurra de verdad.

Auditoría — saber quién cambió qué, y cuándo

En el mundo real: los bancos y las plataformas de pagos mantienen registros de auditoría inmutables de cada movimiento de saldo, exigidos incluso por regulación. Cuando algo sale mal (un fraude, un bug, un reclamo de un cliente), esa traza es la única forma de reconstruir exactamente qué pasó.

Por qué importa a futuro: sin auditoría, un incidente de seguridad se investiga a ciegas; con ella, se puede responder con precisión "quién", "qué" y "cuándo".

Respaldos totales e incrementales — la regla 3-2-1

En el mundo real: equipos de infraestructura siguen la llamada "regla 3-2-1": al menos 3 copias de los datos, en 2 tipos de medio distintos, con 1 copia fuera del sitio (por ejemplo, en la nube). Combinar un respaldo total periódico con binlogs continuos —igual que en este script— es exactamente esa estrategia aplicada a una base de datos.

Por qué importa a futuro: un respaldo que nunca se probó restaurar no es un respaldo, es una suposición — muchos incidentes reales se han agravado al descubrir, ya en plena crisis, que el backup estaba corrupto o incompleto.

PITR (recuperación punto-en-el-tiempo) — no perder "casi nada"

En el mundo real: plataformas de comercio electrónico y bancos usan recuperación punto-en-el-tiempo para restaurar el sistema al segundo exacto antes de un incidente, en vez de perder todo un día de transacciones desde el último respaldo total. GitLab documentó públicamente en 2017 un incidente donde la falta de un plan de backups y PITR bien probado les costó horas de datos de usuarios.

Por qué importa a futuro: la diferencia entre un respaldo diario y PITR puede ser la diferencia entre perder segundos de datos o perder un día entero.

Por qué el "reto final" de este curso es un simulacro

Los equipos de infraestructura serios ejecutan "game days" o simulacros de desastre programados, exactamente como el script 4 de esta sesión: provocan una falla a propósito, en un entorno controlado, para comprobar que el plan de recuperación funciona de verdad — antes de que un incidente real los obligue a descubrirlo bajo presión.

Paso 0 · Preparar el entorno

A diferencia de las sesiones anteriores, aquí no todo se pega en la pestaña SQL de phpMyAdmin: los scripts 2, 3 y 4 son scripts de terminal (bash), pensados para ejecutarse desde la línea de comandos del servidor, no dentro del navegador.

  • Necesitas acceso a una terminal con los clientes mysql y mysqldump instalados (vienen con cualquier instalación de MySQL/MariaDB).
  • El script del binlog (Paso 3) requiere permisos de administrador del servidor para editar my.cnf/my.ini — no es algo que se configure con una simple sentencia SQL.
  • La base juego_online de las Sesiones 1 a 5 debe existir y tener datos, para que el respaldo y el simulacro tengan algo real que proteger.

⚠️ Importante: el script del Paso 5 ejecuta un DROP DATABASE real. Practica todo este simulacro únicamente en un servidor local o de pruebas — nunca en un servidor de producción, y nunca sin haber verificado antes que el respaldo del Paso 2 se generó correctamente.

Los bloques de código de esta guía usan dos estilos: SQL (morado, se pega en phpMyAdmin) y terminal (ámbar, se ejecuta con bash desde la consola). Nunca los confundas.

scripts/01_auditoria_trazas.sql

Paso 1 · Auditoría de datos con un TRIGGER

Antes de poder recuperarte de un incidente, necesitas saber qué pasó. Este script crea una tabla de auditoría y un TRIGGER que registra automáticamente cada vez que cambian las monedas de un jugador — sin que la aplicación tenga que acordarse de anotarlo.

en phpMyAdmin
  1. Pestaña SQL → pega el bloque de abajo (botón Copiar SQL).
  2. Pulsa Continuar.
SQL — pégalo en la pestaña SQL de phpMyAdmin 
-- Sesión 6: Auditoría de datos — herramientas y trazas (MySQL / MariaDB)
-- Registra cambios críticos sobre monedas de jugadores (compras, ajustes de admin)
USE juego_online;

CREATE TABLE IF NOT EXISTS Auditoria_Monedas (
    auditoria_id    INT AUTO_INCREMENT PRIMARY KEY,
    jugador_id      INT NOT NULL,
    monedas_antes   INT NOT NULL,
    monedas_despues INT NOT NULL,
    operacion       VARCHAR(20) NOT NULL,
    usuario_bd      VARCHAR(100) NOT NULL,
    fecha           DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

DROP TRIGGER IF EXISTS auditoria_monedas;

DELIMITER //

CREATE TRIGGER auditoria_monedas
    AFTER UPDATE ON Jugadores
    FOR EACH ROW
BEGIN
    -- MySQL no tiene "IS DISTINCT FROM"; se usa el operador NULL-safe negado
    IF NOT (OLD.monedas <=> NEW.monedas) THEN
        INSERT INTO Auditoria_Monedas (jugador_id, monedas_antes, monedas_despues, operacion, usuario_bd)
        VALUES (OLD.jugador_id, OLD.monedas, NEW.monedas, 'UPDATE', CURRENT_USER());
    END IF;
END //

DELIMITER ;

-- Prueba de traza: cambiar monedas de un jugador y revisar la auditoría
UPDATE Jugadores SET monedas = monedas + 100 WHERE jugador_id = 1;
SELECT * FROM Auditoria_Monedas ORDER BY fecha DESC;

scripts/02_backup_completo.sh

Paso 2 · Respaldo total con mysqldump

Un respaldo total es una fotografía completa de la base de datos en un instante dado. mysqldump es la herramienta de línea de comandos que hace exactamente lo mismo que la pestaña Exportar de phpMyAdmin, pero de forma automatizable (por ejemplo, para programarla con cron).

  • --single-transaction: toma la fotografía sin bloquear las tablas InnoDB, para que el juego pueda seguir recibiendo tráfico mientras se genera el respaldo.
  • --routines --triggers: incluye también los procedimientos almacenados y el trigger de auditoría del Paso 1 — no solo los datos.
  • El archivo se nombra con fecha y hora exactas, para poder identificar y ordenar respaldos.
terminal — ejecutar con bash, NUNCA pegar en phpMyAdmin 
#!/bin/bash
# Sesión 6: Respaldo total (completo) de la base de datos del juego (MySQL / MariaDB)
# Uso: bash 02_backup_completo.sh
#
# Nota: en phpMyAdmin este mismo respaldo se hace desde la interfaz gráfica:
#   selecciona la base "juego_online" -> pestaña "Exportar" -> método "Personalizado"
#   -> formato SQL -> Continuar. Este script es la vía por línea de comandos/automatizada.

set -euo pipefail

DB_NAME="juego_online"
DB_USER="root"
BACKUP_DIR="$(dirname "$0")/../respaldos"
FECHA="$(date +%Y%m%d_%H%M%S)"
ARCHIVO="${BACKUP_DIR}/juego_online_completo_${FECHA}.sql"

mkdir -p "$BACKUP_DIR"

echo "Generando respaldo total de ${DB_NAME}..."
mysqldump -u "$DB_USER" -p --single-transaction --routines --triggers "$DB_NAME" > "$ARCHIVO"

echo "Respaldo completo generado en: $ARCHIVO"
⚠️ Pide la contraseña de root de forma interactiva (-p) — no la escribas dentro del script.

El script arma el nombre del archivo con date +%Y%m%d_%H%M%S, tomando la fecha y hora exactas de tu servidor en el momento de ejecutarlo. Este reloj usa la hora de tu propio navegador para mostrarte un ejemplo en vivo:

scripts/03_backup_incremental_binlog.sh

Paso 3 · Respaldo incremental con el binary log (PITR)

Un respaldo total diario protege contra la pérdida total de datos, pero si el incidente ocurre a las 14:32, ¿qué pasa con todo lo que sucedió desde el respaldo de la medianoche? El binary log (binlog) registra continuamente cada cambio confirmado, permitiendo restaurar la base a cualquier instante exacto — esto se llama recuperación punto-en-el-tiempo (Point-In-Time Recovery, PITR).

terminal — script de referencia/documentación, NUNCA pegar en phpMyAdmin 
#!/bin/bash
# Sesión 6: Respaldo incremental mediante binary log (binlog) — equivalente en
# MySQL/MariaDB al archivado de WAL en PostgreSQL. Documenta la configuración de
# referencia; requiere permisos de administrador sobre el servidor (my.cnf/my.ini).

set -euo pipefail

BINLOG_ARCHIVE_DIR="$(dirname "$0")/../respaldos/binlog_archive"
mkdir -p "$BINLOG_ARCHIVE_DIR"

cat <<'EOF'
Configuración de referencia para respaldos incrementales (PITR) en my.cnf:

  [mysqld]
  log_bin = /var/log/mysql/mysql-bin.log
  server_id = 1
  binlog_format = ROW
  expire_logs_days = 7

Con esto, cada cambio confirmado (INSERT/UPDATE/DELETE) queda registrado en el
binlog. Un respaldo total (02_backup_completo.sh / mysqldump) + los binlogs
generados después permiten restaurar la base de datos a CUALQUIER punto en el
tiempo entre el último respaldo total y el momento justo antes del "ataque".

Flujo del reto final (Sesión 6):
  1. Respaldo base:        mysqldump ... > base.sql          (02_backup_completo.sh)
  2. Binlog continuo:      el servidor lo genera automáticamente con log_bin=ON
  3. Incidente simulado:   se "cae" o corrompe la base de datos
  4. Recuperación PITR:    restaurar base.sql y luego reproducir los binlogs
                           hasta el instante previo al incidente:

     mysqlbinlog --stop-datetime="2026-12-18 23:55:00" \
       /var/log/mysql/mysql-bin.000123 | mysql -u root -p juego_online

En phpMyAdmin puedes revisar los binlogs activos desde Panel principal ->
Estado -> Binary log (si el usuario conectado tiene privilegio REPLICATION CLIENT,
como el rol soporte_sa creado en la Sesión 2).
EOF

echo "Directorio de referencia para binlogs archivados: $BINLOG_ARCHIVE_DIR"
⚠️ Requiere editar my.cnf/my.ini del servidor (acceso de administrador de infraestructura) — no es un cambio que se haga con SQL.

⏱️ Simulador: elige tu punto de recuperación (PITR)

Arrastra el control para elegir el valor de --stop-datetime de mysqlbinlog. Todo lo que ocurrió antes de ese instante se recupera; todo lo que ocurrió después se pierde, aunque haya quedado registrado en el binlog.

Resultado esperado: mover el control hasta el instante justo antes del incidente recupera el 100% de las transacciones reales; detenerse antes de tiempo pierde transacciones válidas innecesariamente; pasarse del incidente es imposible — no hay binlog después de la caída.

Paso 4 · Respaldos calendarizados, de objetos y discos de imagen

Los respaldos de los Pasos 2 y 3 los ejecutaste tú, a mano, en un momento puntual. En producción, nadie confía en que una persona recuerde hacerlo todos los días — el respaldo tiene que pasar solo. Además, no siempre hace falta respaldar toda la base: a veces solo una tabla, o el propio disco completo.

Respaldos calendarizados: que el respaldo se ejecute solo

Un respaldo calendarizado (programado) es exactamente el script del Paso 2, pero disparado automáticamente por el sistema operativo en vez de por una persona — con cron en Linux/macOS o el Programador de tareas en Windows.

terminal (Linux/macOS) — programar el respaldo total cada noche a la 1:00 a.m. 
# Editar el crontab del usuario que administra el servidor
crontab -e

# Agregar esta línea (formato: minuto hora día mes día-semana comando):
0 1 * * * /bin/bash /ruta/al/curso/scripts/02_backup_completo.sh >> /var/log/backup_juego.log 2>&1

# 0 1 * * *  =  todos los días, a la 1:00 a.m.
# Verificar que quedó programado:
crontab -l
⚠️ Comando de terminal real — solo referencia conceptual, no forma parte de los scripts ejecutables del curso.

En Windows, el equivalente es crear una tarea en el Programador de tareas que ejecute 02_backup_completo.sh (vía WSL o Git Bash) todos los días a una hora fija. La idea es la misma: el respaldo deja de depender de que alguien se acuerde de hacerlo.

Respaldos de objetos de BD: no todo o nada

mysqldump juego_online (Paso 2) respalda toda la base. Pero mysqldump también permite respaldar un solo objeto — una tabla, o solo la estructura de un procedimiento — cuando restaurar todo sería exagerado para el problema real:

terminal — respaldar objetos individuales, no toda la base 
# Respaldar SOLO la tabla de auditoría (por ejemplo, antes de purgarla)
mysqldump -u root -p juego_online Auditoria_Monedas > respaldo_auditoria.sql

# Respaldar SOLO los procedimientos almacenados y triggers (sin datos)
mysqldump -u root -p --no-data --routines --triggers juego_online > respaldo_objetos.sql

# Restaurar solo esa tabla en la base (sin tocar el resto)
mysql -u root -p juego_online < respaldo_auditoria.sql

Útil, por ejemplo, si subir_nivel_jugador (Sesión 1) se modifica por error: en vez de restaurar toda la base y perder partidas nuevas, se restaura solo ese procedimiento desde un respaldo de objetos.

Discos de imágenes (snapshots): otra forma de recuperación

Todo lo anterior son respaldos lógicos (archivos .sql con sentencias que reconstruyen los datos). Un disco de imagen (snapshot) es un respaldo físico: una copia congelada de todo el disco o volumen donde vive la base de datos, tomada por la infraestructura (no por MySQL), por ejemplo un snapshot de Amazon EBS o de un disco administrado de Azure.

Tipo de recuperaciónCómo se generaCuándo conviene
Respaldo lógico total (Paso 2)mysqldump completoPortable entre versiones/motores; más lento de restaurar en bases grandes
PITR con binlog (Paso 3)Respaldo total + binary logRecuperar hasta segundos antes del incidente
Respaldo de objetos (arriba)mysqldump de una tabla/rutinaRevertir un error puntual sin tocar el resto de la base
Disco de imagen (snapshot)Snapshot del volumen/disco (EBS, Azure Disk)Restaurar un servidor completo en minutos, tal como estaba en ese instante

Los snapshots son mucho más rápidos de restaurar que reproducir un .sql gigante, pero dependen de la infraestructura de nube o del sistema de discos (LVM), no de MySQL — por eso conviene combinarlos con los respaldos lógicos, nunca depender de un solo tipo.

scripts/04_simulacro_desastre_recuperacion.sh

Paso 5 · Reto final — Simulacro de desastre y recuperación

Este es el reto final del curso: el script elimina intencionalmente la base de datos completa (simulando una caída crítica del servidor) y la restaura desde el último respaldo, verificando automáticamente que ningún jugador perdió su inventario, monedas o progreso.

terminal — contiene un DROP DATABASE real, solo en entorno local/pruebas 
#!/bin/bash
# Sesión 6: RETO FINAL — Simulacro de caída crítica del servidor y recuperación
# Motor: MySQL / MariaDB
# Simula un "ataque DDoS que tumba el centro de datos": se elimina la base de datos
# por completo y se restaura desde el último respaldo, verificando que ningún
# jugador perdió su inventario, monedas o progreso.

set -euo pipefail

DB_NAME="juego_online"
DB_USER="root"
BACKUP_DIR="$(dirname "$0")/../respaldos"
ULTIMO_RESPALDO="$(ls -t "${BACKUP_DIR}"/juego_online_completo_*.sql 2>/dev/null | head -n1)"

if [[ -z "$ULTIMO_RESPALDO" ]]; then
    echo "ERROR: no hay respaldos disponibles. Ejecuta primero 02_backup_completo.sh"
    exit 1
fi

echo "=== Estado ANTES del incidente ==="
mysql -u "$DB_USER" -p "$DB_NAME" \
    -e "SELECT nombre_usuario, nivel, monedas FROM Jugadores ORDER BY jugador_id;" \
    | tee "${BACKUP_DIR}/estado_antes.txt"

echo ""
echo "!!! SIMULANDO ATAQUE / CAÍDA CRÍTICA DEL SERVIDOR PRINCIPAL !!!"
mysql -u "$DB_USER" -p -e "DROP DATABASE ${DB_NAME};"
echo "Base de datos ${DB_NAME} eliminada (incidente simulado)."

echo ""
echo "=== Iniciando recuperación desde respaldo: $ULTIMO_RESPALDO ==="
mysql -u "$DB_USER" -p -e "CREATE DATABASE ${DB_NAME} CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
mysql -u "$DB_USER" -p "$DB_NAME" < "$ULTIMO_RESPALDO"

echo ""
echo "=== Estado DESPUÉS de la recuperación ==="
mysql -u "$DB_USER" -p "$DB_NAME" \
    -e "SELECT nombre_usuario, nivel, monedas FROM Jugadores ORDER BY jugador_id;" \
    | tee "${BACKUP_DIR}/estado_despues.txt"

echo ""
if diff -q "${BACKUP_DIR}/estado_antes.txt" "${BACKUP_DIR}/estado_despues.txt" > /dev/null; then
    echo "RETO SUPERADO: los datos de todos los jugadores se recuperaron sin pérdidas."
else
    echo "ATENCION: hay diferencias entre el estado antes y después. Revisar el respaldo usado."
fi

# Alternativa 100% gráfica en phpMyAdmin (sin línea de comandos):
#   1. Exportar (antes del "ataque"): base juego_online -> pestaña Exportar -> Continuar
#   2. Simular el ataque: base juego_online -> Operaciones -> "Eliminar la base de datos (DROP)"
#   3. Recuperar: crear la base juego_online de nuevo -> pestaña Importar -> subir el .sql exportado
🔥 DROP DATABASE es irreversible sin un respaldo válido. Verifica primero que el Paso 2 generó un archivo real antes de ejecutar esto.

    Resultado esperado: con un respaldo actualizado, el reto se supera y el estado antes/después es idéntico. Con un respaldo desactualizado, la recuperación funciona igual, pero el simulacro señala correctamente las diferencias — la lección real: recuperar es fácil si el respaldo es bueno; lo difícil es no darte cuenta de que ya no lo era.

    🤔 ¿Por qué la comparación usa diff en vez de solo "mirar"?verificación automática

    Con miles de jugadores, comparar el estado antes/después a simple vista no es viable ni confiable. diff -q compara los dos archivos de texto byte a byte y responde con un simple sí/no: son idénticos o no lo son. Automatizar la verificación es lo que permite ejecutar este mismo simulacro con una base de datos real de producción, en segundos, sin depender de que una persona revise fila por fila.

    🚨 ¿Qué se pierde si el respaldo está desactualizado?ventana de pérdida de datos

    Todo lo que haya cambiado entre el momento en que se generó el respaldo total y el momento del incidente. Es exactamente el problema que resuelve el binlog del Paso 3: en vez de aceptar esa "ventana de pérdida", PITR permite reproducir los cambios confirmados después del respaldo, minuto a minuto, hasta justo antes de la caída.
