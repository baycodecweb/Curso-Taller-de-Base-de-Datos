💼 Estos comandos, fuera del aula

Lo que acabas de escribir — PRIMARY KEY, FOREIGN KEY, UNIQUE, INDEX, JOIN, procedimientos almacenados — no son ejercicios de clase. Son las mismas piezas que sostienen sistemas que mueven miles de millones de dólares, y que cuando fallan, se vuelven noticia mundial. Esta es una lista corta de casos reales, uno por cada concepto de esta sesión.

PRIMARY KEY / AUTO_INCREMENT — identificar sin ambigüedad

En el mundo real: los sistemas bancarios y de tarjetas de pago dependen de un identificador único e irrepetible por cada transacción; sin él, sería imposible distinguir un pago real de uno duplicado o fraudulento.

Por qué importa a futuro: cualquier sistema que registre "eventos" (compras, citas médicas, envíos) necesita esta idea — suele ser de las primeras preguntas en una entrevista técnica de bases de datos.

FOREIGN KEY — que los datos no puedan "mentir"

En el mundo real: SABRE, creado en los años 60 por American Airlines e IBM, fue uno de los primeros sistemas de reservas en tiempo real de la historia de la computación, construido después de años de vuelos con overbooking y reservas perdidas por procesos en papel. La regla de que un boleto no puede existir sin un vuelo válido detrás es, en esencia, una llave foránea.

Por qué importa a futuro: cualquier industria con inventario, reservas o citas (aerolíneas, hospitales, hoteles) se apoya en esta misma garantía de integridad.

UNIQUE + control de concurrencia — no vender el mismo asiento dos veces

En el mundo real: en 2022, la altísima demanda por boletos de una gira mundial saturó los sistemas de Ticketmaster: miles de compras fallaron o se duplicaron, con cobertura masiva en medios y hasta una audiencia en el Senado de EE. UU. Es el mismo problema que resolverás en la Sesión 3, bloqueando una fila para que dos jugadores no compren el mismo item único a la vez.

Por qué importa a futuro: comercio electrónico, boletería y videojuegos en vivo viven o mueren según resuelvan bien este problema.

INDEX — la diferencia entre segundos y milisegundos

En el mundo real: Stack Overflow documentó públicamente durante años que atendía millones de visitas diarias con sorprendentemente pocos servidores SQL Server, gracias sobre todo a un diseño de índices y consultas cuidadosamente optimizado — no a fuerza bruta de más máquinas.

Por qué importa a futuro: saber indexar bien puede ahorrarle a una empresa servidores completos (y mucho dinero en la nube).

JOIN + GROUP BY (leaderboards y reportes) — de datos crudos a decisiones

En el mundo real: estudios como Riot Games (League of Legends) documentan públicamente cómo construyen sus sistemas de leaderboards, estadísticas de partidas y matchmaking sobre infraestructura de datos — exactamente el mismo patrón de consultas que armaste en el Paso 3.

Por qué importa a futuro: todo panel de administración, reporte de ventas o dashboard de negocio nace de un JOIN + GROUP BY bien escrito.

Procedimientos almacenados — reglas de negocio que no se pueden saltar

En el mundo real: bancos y aseguradoras suelen centralizar reglas críticas (como el cálculo de intereses o la validación de una póliza) directamente en la base de datos mediante procedimientos almacenados, para que ninguna aplicación externa pueda saltárselas por error o accidente.

Por qué importa a futuro: es una de las razones por las que a los DBA y desarrolladores backend se les paga bien — son quienes garantizan que esas reglas nunca se rompan.

Un adelanto de por qué vas a aprender respaldos (Sesión 6)

En 2017, un ingeniero de GitLab borró por error la base de datos de producción de gitlab.com. La empresa narró el incidente públicamente en tiempo real, y perdieron horas de datos porque sus respaldos automáticos llevaban tiempo fallando en silencio, sin que nadie lo notara. Sigue siendo uno de los casos más citados en la industria del software sobre por qué los respaldos no son opcionales — y por qué hay que probarlos, no solo configurarlos.

Paso 0 · Abrir phpMyAdmin

No necesitas crear la base de datos a mano: el script del Paso 1 incluye CREATE DATABASE IF NOT EXISTS juego_online, así que se crea sola la primera vez que lo ejecutes.

  1. Entra a phpMyAdmin (normalmente http://localhost/phpmyadmin).
  2. Ve a la pestaña SQL en la barra superior — ahí pegarás cada script.

Requiere MySQL 8.0.16+ o MariaDB 10.5+ (por las restricciones CHECK que se usan más adelante, en la Sesión 4).

scripts/01_crear_tablas.sql

Paso 1 · Crear las tablas

Define el modelo relacional completo: Jugadores, Juegos, Items, Inventario_Items, Partidas y Logros, con sus llaves primarias, foráneas e índices básicos.

  • Crea la base juego_online y 6 tablas relacionadas entre sí.
  • Agrega índices sobre Partidas.jugador_id e Inventario_Items.jugador_id.
  • Usa DROP TABLE IF EXISTS al inicio: se puede volver a ejecutar sin errores.
en phpMyAdmin
  1. Pestaña SQL → pega el bloque de abajo (botón Copiar SQL).
  2. Pulsa Continuar.
  3. En el panel izquierdo aparecerá la base juego_online con sus 6 tablas.
SQL — pégalo en la pestaña SQL de phpMyAdmin 
-- Sesión 1: Modelo relacional de la plataforma de juego online
-- Motor: MySQL / MariaDB (compatible con phpMyAdmin)
-- Requiere MySQL 8.0.16+ o MariaDB 10.5+ (soporte de restricciones CHECK)

CREATE DATABASE IF NOT EXISTS juego_online CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE juego_online;

SET FOREIGN_KEY_CHECKS = 0;
DROP TABLE IF EXISTS Logros;
DROP TABLE IF EXISTS Partidas;
DROP TABLE IF EXISTS Inventario_Items;
DROP TABLE IF EXISTS Items;
DROP TABLE IF EXISTS Juegos;
DROP TABLE IF EXISTS Jugadores;
SET FOREIGN_KEY_CHECKS = 1;

CREATE TABLE Jugadores (
    jugador_id      INT AUTO_INCREMENT PRIMARY KEY,
    nombre_usuario  VARCHAR(50)  NOT NULL UNIQUE,
    email           VARCHAR(100) NOT NULL UNIQUE,
    nivel           INT NOT NULL DEFAULT 1,
    experiencia     INT NOT NULL DEFAULT 0,
    monedas         INT NOT NULL DEFAULT 0,
    region          VARCHAR(20) NOT NULL DEFAULT 'AMERICA',
    fecha_registro  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;

CREATE TABLE Juegos (
    juego_id        INT AUTO_INCREMENT PRIMARY KEY,
    nombre          VARCHAR(80) NOT NULL,
    genero          VARCHAR(40),
    fecha_lanzamiento DATE
) ENGINE=InnoDB;

CREATE TABLE Items (
    item_id         INT AUTO_INCREMENT PRIMARY KEY,
    nombre          VARCHAR(80) NOT NULL,
    tipo            VARCHAR(30) NOT NULL,
    rareza          VARCHAR(20) NOT NULL DEFAULT 'comun',
    precio_monedas  INT NOT NULL DEFAULT 0
) ENGINE=InnoDB;

CREATE TABLE Inventario_Items (
    inventario_id   INT AUTO_INCREMENT PRIMARY KEY,
    jugador_id      INT NOT NULL,
    item_id         INT NOT NULL,
    cantidad        INT NOT NULL DEFAULT 1,
    fecha_obtencion DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uq_jugador_item (jugador_id, item_id),
    CONSTRAINT fk_inv_jugador FOREIGN KEY (jugador_id) REFERENCES Jugadores(jugador_id),
    CONSTRAINT fk_inv_item    FOREIGN KEY (item_id) REFERENCES Items(item_id)
) ENGINE=InnoDB;

CREATE TABLE Partidas (
    partida_id      INT AUTO_INCREMENT PRIMARY KEY,
    jugador_id      INT NOT NULL,
    juego_id        INT NOT NULL,
    puntaje         INT NOT NULL DEFAULT 0,
    duracion_seg    INT NOT NULL DEFAULT 0,
    resultado       VARCHAR(20) NOT NULL DEFAULT 'jugada',
    fecha           DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_partida_jugador FOREIGN KEY (jugador_id) REFERENCES Jugadores(jugador_id),
    CONSTRAINT fk_partida_juego   FOREIGN KEY (juego_id) REFERENCES Juegos(juego_id)
) ENGINE=InnoDB;

CREATE TABLE Logros (
    logro_id        INT AUTO_INCREMENT PRIMARY KEY,
    jugador_id      INT NOT NULL,
    nombre_logro    VARCHAR(80) NOT NULL,
    fecha_obtenido  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_logro_jugador FOREIGN KEY (jugador_id) REFERENCES Jugadores(jugador_id)
) ENGINE=InnoDB;

CREATE INDEX idx_partidas_jugador ON Partidas(jugador_id);
CREATE INDEX idx_inventario_jugador ON Inventario_Items(jugador_id);
⚠ terminal (mysql CLI) — NO pegar en phpMyAdmin 
mysql -u root -p < scripts/01_crear_tablas.sql
Esto es un comando de terminal (cmd, PowerShell o bash) — pégalo en una consola, nunca en el cuadro SQL de phpMyAdmin.

Resultado esperado: la base juego_online aparece en el panel izquierdo con 6 tablas y 2 índices, sin errores.

scripts/03_consultas_leaderboard.sql

Paso 3 · Consultas del leaderboard

Cuatro consultas SQL listas para usar: tabla de clasificación general, leaderboard por juego, catálogo de items comprados y ranking de victorias.

¿Qué es un leaderboard y por qué importa?

Un leaderboard (tabla de clasificación) es simplemente un ranking de jugadores ordenado por algún criterio: puntaje, victorias, nivel, etc. Detrás de esa lista tan simple que ves en cualquier juego online hay una consulta SQL con JOIN, GROUP BY y una función de agregación — exactamente lo que vas a construir en este paso.

No es solo una pantalla bonita: para el negocio detrás del juego es una de las piezas de datos más valiosas.

  • Retención de jugadores: ver tu posición (o la de tus amigos) motiva a volver a jugar para superarla — es uno de los mecanismos de "enganche" más usados en la industria.
  • Competencia social: comparar resultados convierte una partida individual en una competencia colectiva, lo que aumenta el tiempo que un jugador pasa en la plataforma.
  • Datos de negocio: el mismo tipo de consulta (agrupar y ordenar) sirve para detectar a los jugadores más activos, los que gastan más monedas, o los que llevan tiempo sin volver.
  • Fundamento técnico transferible: MAX(), SUM(), COUNT(), JOIN y GROUP BY son la base de casi cualquier reporte o panel de estadísticas en una aplicación real, no solo de un juego.

Las 4 consultas de este paso representan 4 casos de uso distintos que verás una y otra vez en el mundo real:

  • 1 · Tabla de Clasificación: el ranking general "todos contra todos" que normalmente se muestra en el menú principal del juego.
  • 2 · Leaderboard por juego: el mismo ranking, pero acotado a un solo título — típico en plataformas que ofrecen varios juegos, como esta.
  • 3 · Catálogo de items comprados: no es un ranking, pero usa el mismo patrón de JOIN que verías en un historial de compras o un inventario visible para el jugador.
  • 4 · Ranking de victorias: una métrica distinta al puntaje acumulado — la tasa de victorias, clave en modos competitivos donde ganar importa más que la cantidad de puntos.
en phpMyAdmin
  1. Pestaña SQL → pega una consulta a la vez (phpMyAdmin solo muestra el resultado de la última si pegas varias juntas).
  2. Pulsa Continuar y revisa la tabla de resultados debajo.
1 · Tabla de Clasificación (Leaderboard) 
SELECT
    j.nombre_usuario,
    j.nivel,
    j.region,
    MAX(p.puntaje) AS mejor_puntaje
FROM Partidas p
JOIN Jugadores j ON j.jugador_id = p.jugador_id
GROUP BY j.jugador_id, j.nombre_usuario, j.nivel, j.region
ORDER BY mejor_puntaje DESC;
2 · Leaderboard por juego específico 
SELECT
    g.nombre AS juego,
    j.nombre_usuario,
    p.puntaje,
    p.fecha
FROM Partidas p
JOIN Jugadores j ON j.jugador_id = p.jugador_id
JOIN Juegos g ON g.juego_id = p.juego_id
WHERE g.nombre = 'Battle Arena Online'
ORDER BY p.puntaje DESC
LIMIT 10;
3 · Catálogo de items comprados 
SELECT
    j.nombre_usuario,
    i.nombre AS item,
    i.rareza,
    ii.cantidad,
    ii.fecha_obtencion
FROM Inventario_Items ii
JOIN Jugadores j ON j.jugador_id = ii.jugador_id
JOIN Items i ON i.item_id = ii.item_id
ORDER BY j.nombre_usuario, ii.fecha_obtencion;
4 · Ranking de victorias por jugador 
SELECT
    j.nombre_usuario,
    SUM(CASE WHEN p.resultado = 'victoria' THEN 1 ELSE 0 END) AS victorias,
    COUNT(p.partida_id) AS partidas_jugadas
FROM Jugadores j
LEFT JOIN Partidas p ON p.jugador_id = j.jugador_id
GROUP BY j.jugador_id, j.nombre_usuario
ORDER BY victorias DESC;

Resultado esperado: 4 tablas de resultados, ordenadas por puntaje/victorias descendente.

Tip: copia y pega cada consulta por separado en el cuadro SQL de phpMyAdmin durante la clase.

scripts/04_procedimiento_subir_nivel.sql

Paso 4 · Procedimiento: subir de nivel

Crea el procedimiento subir_nivel_jugador(jugador_id, experiencia_ganada). Cada 500 puntos de experiencia acumulada sube 1 nivel; el resto se conserva como experiencia restante.

en phpMyAdmin
  1. Pestaña SQL → pega el bloque de abajo, incluido el DELIMITER // ... // (phpMyAdmin lo interpreta igual que la consola de MySQL).
  2. Pulsa Continuar. El procedimiento queda guardado en Rutinas (pestaña de la base de datos).
SQL — pégalo en la pestaña SQL de phpMyAdmin 
-- Sesión 1: Procedimiento almacenado para subir de nivel a un jugador (MySQL / MariaDB)
-- Regla: cada 500 puntos de experiencia acumulada sube 1 nivel; el sobrante se conserva.
USE juego_online;

DROP PROCEDURE IF EXISTS subir_nivel_jugador;

DELIMITER //

CREATE PROCEDURE subir_nivel_jugador(
    IN p_jugador_id INT,
    IN p_experiencia_ganada INT
)
BEGIN
    DECLARE v_experiencia_total INT;
    DECLARE v_niveles_ganados INT;

    SELECT experiencia + p_experiencia_ganada INTO v_experiencia_total
    FROM Jugadores WHERE jugador_id = p_jugador_id;

    IF v_experiencia_total IS NULL THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Jugador no existe';
    END IF;

    SET v_niveles_ganados = FLOOR(v_experiencia_total / 500);

    UPDATE Jugadores
    SET nivel = nivel + v_niveles_ganados,
        experiencia = MOD(v_experiencia_total, 500)
    WHERE jugador_id = p_jugador_id;

    SELECT nivel AS nuevo_nivel, experiencia AS experiencia_restante
    FROM Jugadores WHERE jugador_id = p_jugador_id;
END //

DELIMITER ;

Resultado esperado: el jugador NoobMaster (id 4) sube de nivel 1 a nivel 3, con experiencia restante 210 (10 + 1200 = 1210 → 1210 ÷ 500 = 2 niveles, resto 210).

llamar al procedimiento manualmente 
CALL subir_nivel_jugador(4, 1200);
