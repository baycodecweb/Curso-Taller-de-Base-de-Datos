Sesión 3 — Tráfico Masivo y Concurrencia Semanas 5-7

Simula un "Evento de Lanzamiento": miles de jugadores conectados comprando items al mismo tiempo. El servidor no se puede apagar y dos jugadores no pueden comprar la misma skin única a la vez.

Objetivos:

  • Aplicar cambios de estructura a la base de datos sin interrumpir el servicio.
  • Prevenir condiciones de carrera en compras concurrentes usando SELECT ... FOR UPDATE.
  • Comprender disponibilidad de datos y gestión de rendimiento.

Actividades:

  1. Disponibilidad y SLA: disponibilidad, rendimiento y niveles de servicio (conceptual — Paso 0).
  2. Cambios en caliente: ejecutar scripts/01_alter_tables_sin_downtime.sql (ALGORITHM=INSTANT).
  3. Simulación de concurrencia: ejecutar scripts/02_control_transacciones_deadlocks.sql en dos pestañas de phpMyAdmin a la vez.
  4. Discusión: comparar qué pasaría sin FOR UPDATE (venta duplicada del item único).

Cambios de estructura sin apagar el servidor

Es la diferencia entre un cambio de estructura que el jugador nunca nota, y uno que interrumpe el servicio — por eso el sílabo lo llama "gestión de cambios" y "aseguramiento de la disponibilidad".

Condición de carrera: por qué hace falta FOR UPDATE

Sin bloqueo, ambos jugadores leen "disponible" antes de que el otro confirme la compra. FOR UPDATE obliga al segundo a esperar y releer el dato ya actualizado — es lo que hace comprar_item_unico en el Paso 2.

📂 Recursos de esta sesión

Guía interactiva: Sesion-003-index.html
Scripts: scripts/01_alter_tables_sin_downtime.sql, 02_control_transacciones_deadlocks.sql
Requiere tablas InnoDB (bloqueo de filas con FOR UPDATE).

Criterio de éxito: las columnas nuevas se agregan sin bloquear lecturas/escrituras existentes; de dos llamadas concurrentes a comprar_item_unico con el mismo item único, solo una retorna EXITO.

Jerarquía de roles: cada uno hereda del anterior

GRANT rol_jugador TO rol_moderador; y GRANT rol_moderador TO rol_administrador; — cada rol exterior tiene automáticamente todo lo del rol que envuelve, más sus propios privilegios extra.

Cómo rompe una consulta la inyección SQL

La comilla simple es la clave del ataque: si el backend concatena texto sin más, puede cerrar el literal antes de tiempo y convertir el resto en código SQL real — por eso el procedimiento del Paso 3 nunca concatena, solo recibe parámetros.

Sesión 6 — Respaldos y Recuperación ante Ataques Semanas 14-16

¿Qué pasa si el servidor sufre un ataque DDoS o se cae el centro de datos? Reto final: simular una caída crítica y restablecer las cuentas de los usuarios sin perder compras ni progreso.

Objetivos:

  • Configurar copias de seguridad automáticas (totales e incrementales).
  • Auditar accesos y cambios sobre la base de datos.
  • Ejecutar un simulacro completo de desastre y recuperación.

Actividades:

  1. Auditoría: ejecutar scripts/01_auditoria_trazas.sql — registra cambios críticos mediante un TRIGGER.
  2. Respaldo total: pestaña Exportar de phpMyAdmin, o scripts/02_backup_completo.sh.
  3. Respaldo incremental / binlog: scripts/03_backup_incremental_binlog.sh — recuperación punto-en-el-tiempo (PITR).
  4. Calendarización, objetos y snapshots: conceptual — Paso 4 (programar con cron, respaldar una sola tabla/procedimiento, discos de imagen).
  5. Reto final: ejecutar scripts/04_simulacro_desastre_recuperacion.sh — borra la base intencionalmente y la restaura desde el respaldo.

Por qué el binlog salva "casi todo": PITR

Sin binlog, todo lo ocurrido entre el último respaldo y el incidente se pierde. Con PITR, el simulador del Paso 3 deja elegir el punto exacto de recuperación: solo se pierden los segundos entre el último commit registrado y la caída.

El reto final: simulacro de desastre en 4 pasos

Es el mismo patrón que un "game day" de un equipo de infraestructura real: provocar la falla a propósito para comprobar, con evidencia y no solo con la teoría, que la recuperación funciona.

3. Glosario rápido del curso

Términos que reaparecen entre sesiones — si olvidas uno, vuelve aquí antes de repasar la sesión completa.

DBA / SA / DA (Sesiones 1-2)

DBA (Administrador de la plataforma): control total sobre la base. SA (Soporte Técnico de Infraestructura): mantiene el servidor, sin acceso a datos de negocio. DA (Analista de estadísticas): solo lectura para reportes.

Disponibilidad y SLA (Sesión 3)

Disponibilidad: proporción del tiempo en que el sistema responde correctamente. SLA (Service Level Agreement): compromiso formal de disponibilidad (uptime), latencia y throughput.

Roles y grupos de privilegios (Sesión 4)

Un ROLE en MySQL es un grupo de privilegios con nombre — se asigna una cuenta real a un rol en vez de otorgar permisos uno por uno.

ETL (Sesión 5)

Extract-Transform-Load: extraer datos de un origen, transformarlos, y cargarlos en el destino — el patrón detrás de toda carga masiva, local o en la nube.

PITR (Sesión 6)

Point-In-Time Recovery (recuperación punto-en-el-tiempo): restaurar un respaldo total y luego reproducir el binary log hasta justo antes del incidente, para no perder casi nada.

6. Anexo: SQL Server / PostgreSQL vs MySQL/MariaDB

El sílabo pide SQL Server y PostgreSQL (Sesión 1: "Programación en SQL server y Postgre"); este curso los adapta a MySQL/MariaDB con phpMyAdmin porque es el motor disponible en el laboratorio. Las ideas y la lógica son las mismas — cambia la sintaxis. Usa esta tabla para reconocer el mismo comando en los tres motores, por si trabajas con SQL Server o PostgreSQL en otra materia o en una empresa.

Es como decir "hola" en tres idiomas: cambia la palabra, no el saludo. Toda la tabla de abajo funciona así — mismo problema, tres formas distintas de escribirlo.

  2. ordena los resultados del puntaje más alto al más bajo.
  3. se queda solo con las primeras 10 filas ya ordenadas.

MySQL/MariaDB y PostgreSQL cortan con LIMIT 10 al final de la consulta; SQL Server corta al principio con TOP 10. El resultado que ve el jugador es idéntico en los tres.

¿Por qué importa? Sin LIMIT/TOP, el motor tendría que ordenar y devolver todas las partidas de la tabla —podrían ser miles o millones— solo para que la aplicación se quede con las 10 primeras. Cortar dentro de la base de datos, no después en el código, ahorra memoria, tiempo de red y trabajo del servidor. Lo que este ejemplo quiere demostrar es la idea central de todo este anexo: los tres motores resuelven el mismo problema de rendimiento, solo cambia la palabra clave que usan para pedirlo.

  2. consulta si el item ya fue vendido.
  3. específicamente el item con ID 1.
  4. bloquea esa fila hasta que termine la transacción.
  5. aquí iría el UPDATE que marca el item como vendido.
  6. guarda los cambios y libera el bloqueo.

La idea es la misma en los tres motores: mientras el Jugador A tiene el candado sobre la fila, el Jugador B tiene que esperar — así nunca se vende la misma skin dos veces (lo ves a fondo en el diagrama de la Sesión 3).

¿Por qué importa? Sin este candado, los dos jugadores podrían leer "disponible" casi al mismo tiempo y los dos terminarían comprando el mismo item único — una condición de carrera que en un juego real significa vender una skin que ya no existe, o cobrarle a alguien por algo que nunca recibe. Bloquear la fila obliga a que las compras pasen de una en una. Lo que este ejemplo quiere demostrar es que este control de concurrencia no es un detalle de sintaxis: es la diferencia entre un evento de lanzamiento que funciona y uno que genera compras dobles y reclamos — por eso los tres motores, cada uno a su manera, ofrecen una forma de bloquear la fila.

DELIMITER //

CREATE PROCEDURE comprar_item_unico(
    IN p_jugador_id INT,
    IN p_item_id INT,
    OUT p_resultado VARCHAR(255)
)
BEGIN
    DECLARE v_vendido  BOOLEAN;
    DECLARE v_precio   INT;
    DECLARE v_monedas  INT;

    START TRANSACTION;

    -- FOR UPDATE bloquea la fila hasta que esta transacción termine (COMMIT/ROLLBACK),
    -- evitando que dos compras concurrentes lean "vendido = false" al mismo tiempo.
    SELECT vendido, precio_monedas INTO v_vendido, v_precio
    FROM Items
    WHERE item_id = p_item_id AND es_unico = TRUE
    FOR UPDATE;

    IF v_vendido THEN
        SET p_resultado = 'RECHAZADO: el item único ya fue vendido a otro jugador.';
        ROLLBACK;
    ELSE
        SELECT monedas INTO v_monedas FROM Jugadores WHERE jugador_id = p_jugador_id;

        IF v_monedas < v_precio THEN
            SET p_resultado = 'RECHAZADO: monedas insuficientes.';
            ROLLBACK;
        ELSE
            UPDATE Items SET vendido = TRUE WHERE item_id = p_item_id;
            UPDATE Jugadores SET monedas = monedas - v_precio WHERE jugador_id = p_jugador_id;
            INSERT INTO Inventario_Items (jugador_id, item_id, cantidad)
                VALUES (p_jugador_id, p_item_id, 1)
                ON DUPLICATE KEY UPDATE cantidad = cantidad + 1;

            SET p_resultado = CONCAT('EXITO: item unico vendido al jugador ', p_jugador_id);
            COMMIT;
        END IF;
    END IF;
END //

DELIMITER ;

INSERT INTO Partidas_Fragmentada (jugador_id, juego_id, region, puntaje, duracion_seg, resultado, fecha)
WITH RECURSIVE secuencia AS (
    SELECT 1 AS n
    UNION ALL
    SELECT n + 1 FROM secuencia WHERE n < 5000

#!/bin/bash
# Sesión 6: Respaldo incremental mediante binary log (binlog) — equivalente en
# MySQL/MariaDB al archivado de WAL en PostgreSQL. Documenta la configuración de
# referencia; requiere permisos de administrador sobre el servidor (my.cnf/my.ini).

set -euo pipefail

BINLOG_ARCHIVE_DIR="$(dirname "$0")/../respaldos/binlog_archive"
mkdir -p "$BINLOG_ARCHIVE_DIR"

cat <<'EOF'
Configuración de referencia para respaldos incrementales (PITR) en my.cnf:

  [mysqld]
  log_bin = /var/log/mysql/mysql-bin.log
  server_id = 1
  binlog_format = ROW
  expire_logs_days = 7

Con esto, cada cambio confirmado (INSERT/UPDATE/DELETE) queda registrado en el
binlog. Un respaldo total (02_backup_completo.sh / mysqldump) + los binlogs
generados después permiten restaurar la base de datos a CUALQUIER punto en el
tiempo entre el último respaldo total y el momento justo antes del "ataque".

Flujo del reto final (Sesión 6):
  1. Respaldo base:        mysqldump ... > base.sql          (02_backup_completo.sh)
  2. Binlog continuo:      el servidor lo genera automáticamente con log_bin=ON
  3. Incidente simulado:   se "cae" o corrompe la base de datos
  4. Recuperación PITR:    restaurar base.sql y luego reproducir los binlogs
                           hasta el instante previo al incidente:

     mysqlbinlog --stop-datetime="2026-12-18 23:55:00" \
       /var/log/mysql/mysql-bin.000123 | mysql -u root -p juego_online

En phpMyAdmin puedes revisar los binlogs activos desde Panel principal ->
Estado -> Binary log (si el usuario conectado tiene privilegio REPLICATION CLIENT,
como el rol soporte_sa creado en la Sesión 2).
EOF

echo "Directorio de referencia para binlogs archivados: $BINLOG_ARCHIVE_DIR"
#!/bin/bash
# Sesión 6: RETO FINAL — Simulacro de caída crítica del servidor y recuperación
# Motor: MySQL / MariaDB
# Simula un "ataque DDoS que tumba el centro de datos": se elimina la base de datos
# por completo y se restaura desde el último respaldo, verificando que ningún
# jugador perdió su inventario, monedas o progreso.

set -euo pipefail

DB_NAME="juego_online"
DB_USER="root"
BACKUP_DIR="$(dirname "$0")/../respaldos"
ULTIMO_RESPALDO="$(ls -t "${BACKUP_DIR}"/juego_online_completo_*.sql 2>/dev/null | head -n1)"

if [[ -z "$ULTIMO_RESPALDO" ]]; then
    echo "ERROR: no hay respaldos disponibles. Ejecuta primero 02_backup_completo.sh"
    exit 1
fi

echo "=== Estado ANTES del incidente ==="
mysql -u "$DB_USER" -p "$DB_NAME" \
    -e "SELECT nombre_usuario, nivel, monedas FROM Jugadores ORDER BY jugador_id;" \
    | tee "${BACKUP_DIR}/estado_antes.txt"

echo ""
echo "!!! SIMULANDO ATAQUE / CAÍDA CRÍTICA DEL SERVIDOR PRINCIPAL !!!"
mysql -u "$DB_USER" -p -e "DROP DATABASE ${DB_NAME};"
echo "Base de datos ${DB_NAME} eliminada (incidente simulado)."

echo ""
echo "=== Iniciando recuperación desde respaldo: $ULTIMO_RESPALDO ==="
mysql -u "$DB_USER" -p -e "CREATE DATABASE ${DB_NAME} CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
mysql -u "$DB_USER" -p "$DB_NAME" < "$ULTIMO_RESPALDO"

echo ""
echo "=== Estado DESPUÉS de la recuperación ==="
mysql -u "$DB_USER" -p "$DB_NAME" \
    -e "SELECT nombre_usuario, nivel, monedas FROM Jugadores ORDER BY jugador_id;" \
    | tee "${BACKUP_DIR}/estado_despues.txt"

echo ""
if diff -q "${BACKUP_DIR}/estado_antes.txt" "${BACKUP_DIR}/estado_despues.txt" > /dev/null; then
    echo "RETO SUPERADO: los datos de todos los jugadores se recuperaron sin pérdidas."
else
    echo "ATENCION: hay diferencias entre el estado antes y después. Revisar el respaldo usado."
fi
