Fragmentación por Regiones y Carga Masiva

Guía visual de uso de los scripts SQL — particionado por región, índices de matchmaking y carga ETL de miles de partidas

💼 Estos conceptos, fuera del aula

Separar datos por región, cargar miles de registros de golpe y hacer que una búsqueda responda al instante no son problemas exclusivos de los videojuegos — son el pan de cada día de cualquier plataforma que crece más allá de un solo servidor.

Fragmentación por región — así escalan los juegos multijugador reales

En el mundo real: juegos como League of Legends, Fortnite o Valorant operan literalmente servidores separados por región (NA, EU, LATAM, Asia) para mantener baja la latencia de red y que cada región soporte su propio volumen de tráfico sin saturar a las demás — es la misma idea de PARTITION BY LIST COLUMNS(region), llevada a servidores físicos completos.

Por qué importa a futuro: a medida que una plataforma crece, una sola base de datos monolítica se vuelve un cuello de botella; fragmentar por una clave natural (región, cliente, fecha) es una de las primeras estrategias para escalar horizontalmente.

ETL y carga masiva — cómo migran datos las empresas reales

En el mundo real: cuando una empresa migra de un sistema antiguo a uno nuevo, o sincroniza datos entre la nube y sus servidores, usa herramientas ETL (Extract-Transform-Load) como AWS Glue, Azure Data Factory o Talend para mover millones de registros por lotes, sin apagar el servicio en producción.

Por qué importa a futuro: cargar datos masivos "a mano", fila por fila, es inviable a esa escala; entender el patrón extraer-transformar-cargar es la base de cualquier pipeline de datos moderno.

Índices — la diferencia entre milisegundos y minutos

En el mundo real: buscadores como Google o marketplaces como Amazon dependen de índices (y estructuras aún más complejas) para que una búsqueda entre miles de millones de registros responda en milisegundos, no en minutos. Un sistema de matchmaking con millones de partidas jugadas enfrenta exactamente el mismo problema, a menor escala.

Por qué importa a futuro: el mismo query, con o sin el índice correcto, puede ser la diferencia entre una app que se siente instantánea y una que los usuarios abandonan por lenta.

Por qué particionar no reemplaza el buen diseño

Fragmentar tablas y usar CTEs recursivas o LOAD DATA INFILE resuelve problemas de volumen, pero como advierte la nota del script 1, particionar tiene costos reales — por ejemplo, MySQL/MariaDB no permiten FOREIGN KEY hacia o desde una tabla particionada. Cada decisión de escalado es un balance, no una solución mágica gratuita.

Por eso Partidas_Fragmentada no tiene claves foráneas explícitas — es una limitación real del motor, y también la lección de esta sesión: en sistemas verdaderamente distribuidos, la integridad referencial entre fragmentos casi siempre se controla en la aplicación, no en la base de datos.

scripts/01_fragmentacion_particiones_region.sql

Paso 1 · Fragmentar Partidas por región

Imagina dos servidores físicos: uno en América y otro en Europa. En vez de que un jugador europeo consulte siempre un servidor lejano, cada partida se guarda en el fragmento (partición) de su propia región. PARTITION BY LIST COLUMNS(region) le pide a MySQL que, por dentro, mantenga la tabla dividida físicamente así, aunque para quien la consulta siga pareciendo una sola tabla.

  • Se crea Partidas_Fragmentada con dos particiones: p_america y p_europa.
  • Los datos existentes de Partidas se migran, tomando la región desde el jugador dueño de cada partida.
  • Un EXPLAIN filtrado por región demuestra el partition pruning: MySQL ni siquiera abre el fragmento que no necesita.
en phpMyAdmin
  1. Pestaña SQL → pega el bloque de abajo (botón Copiar SQL).
  2. Pulsa Continuar.
SQL — pégalo en la pestaña SQL de phpMyAdmin 
-- Sesión 5: Fragmentación de tablas por región (Servidor América / Servidor Europa)
-- Motor: MySQL 8.0+ / MariaDB 10.5+ (PARTITION BY LIST COLUMNS)
--
-- IMPORTANTE: MySQL/MariaDB NO permiten claves foráneas (FOREIGN KEY) hacia o desde
-- una tabla particionada. Esto no es una limitación del script: es una restricción
-- real del motor, y refleja un problema genuino de las bases de datos distribuidas
-- (un fragmento en el "Servidor Europa" no puede validar en tiempo real una fila que
-- vive físicamente en el "Servidor América"). La integridad referencial se controla
-- en la capa de aplicación en vez de con FK.

USE juego_online;

DROP TABLE IF EXISTS Partidas_Fragmentada;

CREATE TABLE Partidas_Fragmentada (
    partida_id      INT AUTO_INCREMENT,
    jugador_id      INT NOT NULL,
    juego_id        INT NOT NULL,
    region          VARCHAR(20) NOT NULL,
    puntaje         INT NOT NULL DEFAULT 0 CHECK (puntaje >= 0),
    duracion_seg    INT NOT NULL DEFAULT 0,
    resultado       VARCHAR(20) NOT NULL DEFAULT 'jugada',
    fecha           DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (partida_id, region)
) ENGINE=InnoDB
PARTITION BY LIST COLUMNS(region) (
    PARTITION p_america VALUES IN ('AMERICA'),
    PARTITION p_europa  VALUES IN ('EUROPA')
);

-- Migramos los datos históricos de Partidas hacia la tabla fragmentada,
-- tomando la región desde el jugador (simulando la sincronización entre servidores)
INSERT INTO Partidas_Fragmentada (jugador_id, juego_id, region, puntaje, duracion_seg, resultado, fecha)
SELECT p.jugador_id, p.juego_id, j.region, p.puntaje, p.duracion_seg, p.resultado, p.fecha
FROM Partidas p
JOIN Jugadores j ON j.jugador_id = p.jugador_id;

-- Verificar que las consultas filtradas por región solo tocan su fragmento
-- (partition pruning): ejecutar y observar la columna "partitions" del plan
-- (en MySQL 8 / MariaDB, EXPLAIN ya incluye esa columna por defecto)
EXPLAIN SELECT * FROM Partidas_Fragmentada WHERE region = 'AMERICA';

-- En MySQL 8.0.18+/MariaDB también puedes usar:
-- EXPLAIN ANALYZE SELECT * FROM Partidas_Fragmentada WHERE region = 'AMERICA';

scripts/02_indices_matchmaking.sql

Paso 2 · Índices para que el matchmaking responda en milisegundos

El matchmaking busca jugadores de nivel similar dentro de la misma región, ordenando por su mejor puntaje reciente. Sin índice, esto obliga a MySQL a un escaneo completo (type: ALL) sobre miles o millones de partidas cada vez que alguien busca partida.

  • idx_partidas_frag_region_fecha: acelera filtrar por región y ordenar por fecha reciente.
  • idx_partidas_frag_jugador: acelera el JOIN entre partidas y su jugador.
  • idx_jugadores_region_nivel: acelera filtrar jugadores por región y rango de nivel.

MySQL no soporta CREATE INDEX IF NOT EXISTS de forma universal (MariaDB sí). Si vuelves a ejecutar este script, borra antes los índices con DROP INDEX <nombre> ON <tabla>; para evitar el error "Duplicate key name".

-- Sesión 5: Índices para que el matchmaking responda en milisegundos
-- Motor: MySQL / MariaDB
-- Nota: a diferencia de PostgreSQL, MySQL no soporta CREATE INDEX IF NOT EXISTS de forma
-- universal (MariaDB sí, MySQL no). Si vuelves a ejecutar este script, borra antes los
-- índices con DROP INDEX <nombre> ON <tabla>; para evitar el error "Duplicate key name".
USE juego_online;

-- El matchmaking busca jugadores de nivel similar dentro de la misma región,
-- ordenando por su mejor puntaje reciente. Sin índice, esto obliga a un escaneo
-- completo (ALL) sobre miles/millones de partidas.

CREATE INDEX idx_partidas_frag_region_fecha
    ON Partidas_Fragmentada (region, fecha DESC);

CREATE INDEX idx_partidas_frag_jugador
    ON Partidas_Fragmentada (jugador_id);

CREATE INDEX idx_jugadores_region_nivel
    ON Jugadores (region, nivel);

-- Consulta típica de matchmaking: jugadores de nivel cercano en la misma región,
-- con su mejor puntaje reciente
EXPLAIN
SELECT j.jugador_id, j.nombre_usuario, j.nivel, MAX(p.puntaje) AS mejor_puntaje_reciente
FROM Jugadores j
JOIN Partidas_Fragmentada p ON p.jugador_id = j.jugador_id AND p.region = j.region
WHERE j.region = 'AMERICA'
  AND j.nivel BETWEEN 10 AND 15
GROUP BY j.jugador_id, j.nombre_usuario, j.nivel
ORDER BY mejor_puntaje_reciente DESC
LIMIT 10;

-- Comparar el plan (columna "key" usada vs "type: ALL") antes y después de crear
-- los índices ejecutando: DROP INDEX idx_jugadores_region_nivel ON Jugadores;
-- y volviendo a correr el EXPLAIN.

Paso 3 · Carga masiva tipo ETL

Simula la importación de un archivo externo (CSV) con historial de partidas: se generan 5000 partidas simuladas con una CTE recursiva (equivalente educativo a LOAD DATA INFILE) y se insertan directamente en Partidas_Fragmentada, repartiéndose entre los fragmentos p_america y p_europa según la región de cada jugador.

en phpMyAdmin
  1. Pestaña SQL → pega el bloque de abajo → Continuar.
  2. Si usas MySQL 8 y aparece un error de recursión, descomenta antes la línea SET SESSION cte_max_recursion_depth = 10000;.
SQL — pégalo en la pestaña SQL de phpMyAdmin 
-- Sesión 5: Carga masiva tipo ETL — miles de registros de partidas históricas
-- Motor: MySQL 8.0+ / MariaDB 10.2+ (WITH RECURSIVE)
-- Simula la importación de un archivo externo (CSV) con historial de partidas
-- desde la nube hacia el servidor regional correspondiente.

USE juego_online;

-- Solo en MySQL 8 (por defecto limita la recursión a 1000 niveles; MariaDB no
-- tiene esta restricción y esta línea se puede omitir):
-- SET SESSION cte_max_recursion_depth = 10000;

-- 1) Generamos 5000 partidas históricas simuladas con una CTE recursiva
--    (equivalente educativo a "importar un archivo CSV masivo" vía LOAD DATA INFILE)
INSERT INTO Partidas_Fragmentada (jugador_id, juego_id, region, puntaje, duracion_seg, resultado, fecha)
WITH RECURSIVE secuencia AS (
    SELECT 1 AS n
    UNION ALL
    SELECT n + 1 FROM secuencia WHERE n < 5000
)
SELECT
    j.jugador_id,
    FLOOR(RAND() * 2) + 1 AS juego_id,
    j.region,
    FLOOR(RAND() * 9000) AS puntaje,
    FLOOR(RAND() * 900) + 60 AS duracion_seg,
    ELT(FLOOR(RAND() * 2) + 1, 'victoria', 'derrota') AS resultado,
    NOW() - INTERVAL FLOOR(RAND() * 180) DAY AS fecha
FROM secuencia
JOIN Jugadores j
    ON j.jugador_id = ((secuencia.n MOD (SELECT COUNT(*) FROM Jugadores)) + 1);

-- 2) Verificación del volumen cargado por región (extracción/transformación/carga completada)
SELECT region, COUNT(*) AS total_partidas
FROM Partidas_Fragmentada
GROUP BY region
ORDER BY region;

-- Nota (equivalencia con herramientas reales de ETL/nube):
--   - MySQL/MariaDB: LOAD DATA INFILE '/ruta/historico.csv' INTO TABLE Partidas_Fragmentada
--       FIELDS TERMINATED BY ',' LINES TERMINATED BY '\n' IGNORE 1 ROWS;
--   - phpMyAdmin: pestaña "Importar" de la tabla, formato CSV, mapeo de columnas.
--   - Nube: AWS DMS, Azure Data Factory, o mysqldump/mysql para sincronizar
--     entre el Servidor América y el Servidor Europa.

🤔 ¿Por qué exactamente 3000 y 2000, y no números al azar?reparto determinista

Lo aleatorio (RAND()) en este script solo afecta al puntaje, la duracion_seg, el resultado y la fecha de cada partida — nunca a qué jugador ni a qué región pertenece. El jugador se asigna con secuencia.n MOD (SELECT COUNT(*) FROM Jugadores), que reparte las 5000 filas en partes exactamente iguales entre los 5 jugadores (1000 cada uno). Como 3 jugadores son de AMERICA y 2 de EUROPA, el resultado siempre es 3000/2000, sin importar cuántas veces ejecutes el script.

📦 ¿Esto es lo mismo que LOAD DATA INFILE?equivalencia educativa

No exactamente, pero cumple el mismo propósito en el aula: generar un volumen grande de datos sin depender de subir un archivo .csv real al servidor. En un caso real de producción, LOAD DATA INFILE (o la pestaña "Importar" de phpMyAdmin) es la herramienta apropiada para volúmenes de miles o millones de filas desde un archivo — la CTE recursiva aquí es un atajo pedagógico para lograr un resultado similar con una sola sentencia SQL, sin archivos externos.

⚠️ ¿Por qué a veces falla con un error de recursión?límite de MySQL 8

MySQL 8 limita por defecto las CTE recursivas a 1000 niveles (cte_max_recursion_depth), y esta secuencia necesita llegar a 5000. La línea comentada SET SESSION cte_max_recursion_depth = 10000; sube ese límite para la sesión actual. MariaDB no tiene esta restricción por defecto, así que ahí ese paso no es necesario.

Paso 4 · Carga y descarga en la nube

La CTE recursiva del Paso 3 simuló la carga masiva dentro del propio servidor MySQL. En un caso real, buena parte de esos datos históricos no nace ahí: viaja desde o hacia un almacenamiento en la nube (AWS S3, Azure Blob Storage, Google Cloud Storage). Este paso es conceptual — no requiere una cuenta de nube real — y conecta el ETL que ya construiste con cómo se ve ese mismo movimiento de datos "hacia afuera" del servidor.

Dos direcciones: carga (subir) y descarga (bajar)

  • Carga a la nube (upload): exportar datos o un respaldo desde juego_online y subirlos a un almacenamiento en la nube — por ejemplo, para compartir el histórico de partidas entre el Servidor América y el Servidor Europa, o para guardarlo antes de una migración.
  • Descarga desde la nube (download): el camino inverso — traer un archivo que vive en la nube (un CSV, un respaldo, un dataset de otro equipo) hacia el servidor local, para cargarlo con LOAD DATA INFILE o la pestaña Importar de phpMyAdmin, tal como se documentó en el Paso 3.

Es exactamente el mismo patrón Extract → Transform → Load del Paso 3, solo que el origen o el destino ya no es "la misma base de datos", sino un almacenamiento remoto.

⚠ comandos de terminal/CLI reales — NO se pegan en phpMyAdmin, son solo referencia conceptual 
# 1) Exportar (respaldo lógico) desde MySQL
mysqldump -u root -p juego_online Partidas_Fragmentada > historico_partidas.sql

# 2) CARGA: subir ese archivo a almacenamiento en la nube
aws s3 cp historico_partidas.sql s3://mi-bucket-juego/backups/
az storage blob upload --container-name backups --file historico_partidas.sql

# 3) DESCARGA: bajar un archivo que vive en la nube hacia el servidor
aws s3 cp s3://mi-bucket-juego/import/nuevas_partidas.csv ./nuevas_partidas.csv

# 4) Cargar el archivo descargado, igual que en el Paso 3
mysql -u root -p juego_online -e "LOAD DATA INFILE './nuevas_partidas.csv' INTO TABLE Partidas_Fragmentada FIELDS TERMINATED BY ',' LINES TERMINATED BY '\n' IGNORE 1 ROWS;"
Esto son comandos de terminal (bash/PowerShell) y CLI de proveedores cloud — se muestran como referencia conceptual, no para ejecutar en este curso.
